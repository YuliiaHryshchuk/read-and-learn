# Read & Learn — веб-приложение для чтения по методу Франка

Дата начала: 17 сентября 2026 года

Последняя актуализация: 10 октября 2026 года

## 1. Цели проекта

Read & Learn помогает разбирать и сохранять учебные тексты.

Пользователь должен иметь возможность:

- ввести или вставить исходный текст вручную;
- выбрать язык перевода и пояснений;
- получить адаптацию по методу Франка: исходные фрагменты, перевод и полезные пояснения;
- сохранить готовый материал в личную библиотеку;
- позже открыть материал без нового AI-запроса, читать, редактировать или удалить его;
- в дополнительном сценарии выбрать или сфотографировать изображение с текстом, распознать текст и перенести его в обычную форму создания материала.

OCR является способом ввода текста, а не отдельным типом материала. После распознавания действует тот же flow, что и после ручного ввода.

## 2. Постоянные продуктовые правила

### 2.1. Языки

- Интерфейс приложения и все элементы управления пишутся на английском языке.
- Текущий учебный сценарий принимает испанский исходный текст; исходный язык пока задан константой `Spanish`.
- Исходный язык и язык перевода и пояснений являются отдельными параметрами и хранятся раздельно.
- Пользователь выбирает язык перевода и пояснений; отдельного выбора исходного языка в основном текстовом flow пока нет.
- Перевод и весь пояснительный текст должны быть целиком на выбранном целевом языке.
- Пример в AI-инструкции используется только при совпадении его языка с выбранным целевым языком.

### 2.2. Формат адаптации

Приложение самостоятельно делит исходный текст на фрагменты и назначает им ID. Модель возвращает только перевод и пояснение для каждого известного ID. Исходный текст никогда не берётся из ответа модели.

```json
{
  "fragment-1": {
    "translation": "...",
    "explanation": "term — explanation\nterm — explanation"
  }
}
```

Требования к ответу:

- каждый запрошенный ID присутствует ровно один раз;
- посторонние ID и поля запрещены;
- `translation` и `explanation` являются строками;
- структура проверяется во время выполнения до отображения или сохранения;
- невалидный ответ не считается успешной адаптацией;
- AI-ответ отображается только как экранированный текст и не передаётся в `dangerouslySetInnerHTML`, `eval`, SQL, команды ОС, URL или имена файлов.

### 2.3. Деление исходного текста

- Словом считается непустая последовательность символов между пробелами или границами строки.
- Целевой фрагмент содержит от 5 до 50 слов и по возможности заканчивается предложением.
- Если добавление следующего предложения превышает 50 слов, граница ставится после предыдущего предложения.
- Предложение длиннее 50 слов принудительно делится на блоки не более 50 слов.
- Короткий остаток по возможности присоединяется или перераспределяется без превышения лимита.
- `Intl.Segmenter` для этого не используется.

### 2.4. Требования к пояснениям

- Пояснение содержит информацию сверх полного перевода: неочевидные значения, выражения, грамматику в контексте, местоименные связи и вероятные опечатки.
- Обычный словарный перевод очевидного слова сам по себе не считается пояснением.
- Для личной формы глагола указываются инфинитив, время, наклонение, лицо и число.
- Для инфинитива, герундия и причастия указывается соответствующая неличная форма без выдуманного времени или лица.

### 2.5. Ограничения ввода

- Пользователь может продолжать ввод после 300 слов, но такой текст нельзя отправить на генерацию или сохранить до исправления превышения.
- Основной жёсткий предел исходного текста — 3000 символов.
- Интерфейс должен явно объяснять превышение лимита, а не молча отклонять действие.
- Текст, полученный через OCR, подчиняется тем же ограничениям.

### 2.6. Отображение материала

- Каждый фрагмент показывает неизменённый исходный отрывок и позволяет независимо раскрывать перевод и пояснение.
- При первом открытии результата развёрнут первый фрагмент, остальные свёрнуты.
- В раскрытом фрагменте объяснение открыто, а перевод изначально скрыт.
- Доступны действия раскрыть или свернуть все фрагменты.
- Исходный отрывок и перевод показываются целиком; длинное объяснение может иметь внутреннюю прокрутку.
- Интерфейс должен полноценно работать на desktop и mobile.

## 3. Постоянные технические и организационные решения

### 3.1. Основной стек

| Область              | Решение                                                  |
| -------------------- | -------------------------------------------------------- |
| Язык разработки      | TypeScript                                               |
| UI                   | React и Next.js                                          |
| Стили                | SCSS и SCSS Modules                                      |
| AI                   | Puter AI, `gpt-5.4-mini` через `azure-openai-responses`  |
| Авторизация          | Puter                                                    |
| Локальная разработка | Docker Compose, Next.js dev и локальная D1               |
| Тесты                | Vitest; live-проверки Puter выполняются отдельно вручную |

Отдельный Python-сервис и собственная модель для текущего объёма задач не планируются.

### 3.2. Почему выбран Puter

Puter выбран не только как способ вызвать AI-модель, но и как часть финансовой и пользовательской архитектуры проекта.

- AI-запросы выполняются за счёт allowance или приобретённых кредитов аккаунта Puter самого пользователя. Владельцу Read & Learn не нужно оплачивать токены всех пользователей из общего API-аккаунта.
- Приложению не требуется создавать собственный биллинг: принимать платежи за AI-запросы, учитывать баланс, распределять лимиты или блокировать перерасход.
- Read & Learn не хранит платёжные данные пользователя и не принимает на себя связанные с ними требования безопасности и обработки чувствительной информации.
- Лимиты и расходы изолированы на уровне отдельных аккаунтов Puter. Один пользователь не может израсходовать общий бюджет приложения и повлиять на доступ остальных пользователей.
- Puter одновременно предоставляет регистрацию, вход и пользовательскую сессию. Это позволяет не разрабатывать отдельную систему учётных записей, восстановления пароля и хранения authentication credentials.

Read & Learn по-прежнему отвечает за понятную обработку ошибок Puter: отсутствие авторизации, исчерпание allowance или кредитов, необходимость платного тарифа, rate limit и временную недоступность провайдера.

### 3.3. Docker и локальная разработка

- Docker Compose остаётся поддерживаемым способом локального запуска и передачи проекта другим разработчикам.
- Текущий Compose-проект называется `read-and-learn` и запускает один web-контейнер.
- Контейнер применяет локальные D1-миграции, поднимает Cloudflare Pages runtime и проксирует Next.js dev server.
- Приложение доступно по адресу `http://localhost:3000`.
- Локальные данные D1 сохраняются в `.wrangler`.
- PostgreSQL-контейнер в актуальном Compose не используется.
- Закреплённая версия Wrangler поддерживает текущий proxy-dev flow; предупреждение о будущем удалении proxy-режима остаётся основанием позже пересмотреть локальный запуск.

### 3.4. Git и документация

- Названия и описания коммитов пишутся на английском языке.
- Прямой push в `main` защищён версионируемым `pre-push` hook; аварийный обход возможен через `--no-verify`.
- Архитектурные решения фиксируются в этом документе по датам, чтобы старое состояние не смешивалось с актуальным.

## 4. Безопасность и постоянные риски

### 4.1. Puter и пользовательские данные

- Puter-токен является секретом. Он передаётся только по HTTPS в `Authorization`, не сохраняется в БД, не включается в URL и не должен попадать в логи.
- Backend не доверяет username, email или владельцу, переданному браузером. Владение материалом определяется только после проверки токена и получения стабильного `puter_user_uuid`.
- Выход пользователя должен очищать состояние авторизации и пользовательские локальные данные приложения.
- Исходный текст и AI-инструкция передаются Puter и выбранному внешнему провайдеру модели. Перед публичным релизом это необходимо отразить в политике конфиденциальности.
- Доступность моделей, стоимость, allowance и ограничения Puter могут меняться; постоянные значения не зашиваются в UI.
- Реальный Puter login popup, загрузка SDK и AI-запрос не покрываются обычными unit-тестами и требуют ручного smoke-сценария.

### 4.2. Prompt injection и недоверенный контент

- Любой пользовательский текст считается недоверенными данными. Инструкции внутри него должны переводиться и объясняться, а не выполняться.
- Системная инструкция и исходный текст передаются модели раздельно.
- AI-запрос не получает tools, web search, выполнение кода, доступ к D1, файловой системе или секретам.
- Приложение само создаёт ID фрагментов и проверяет точное соответствие ответа.
- Безопасность строится не только на промпте, но и на отсутствии у модели технической возможности выполнять действия с побочным эффектом.

### 4.3. Клиент и инфраструктура

- XSS может привести к краже Puter-токена, поэтому запрещена небезопасная HTML-вставка и требуется контроль сторонних зависимостей.
- Строгая CSP и security headers остаются отдельной задачей: политика не должна ломать встроенные Next.js-скрипты статического export и Puter login popup.
- Cloudflare, Puter или внешний AI-провайдер могут быть временно недоступны. Ошибка не должна приводить к потере введённого текста или показываться как успешная адаптация.
- Доступность Cloudflare может различаться по регионам; это нужно учитывать при выборе целевой аудитории и резервного hosting-варианта.
- Rate limits, quotas и privacy-conscious monitoring ещё требуют отдельного решения.

## 5. Состояние проекта на 27 сентября 2026 года

### 5.1. Статус

Рабочий прототип уже умел принимать испанский текст, отправлять structured request через Puter AI, проверять ответ и показывать адаптацию. Хранение материалов, библиотека и backend-интеграция ещё не были реализованы.

### 5.2. Архитектура на эту дату

```text
Браузер: React / Next.js
       |
       +---- Puter Auth
       |
       +---- Puter AI ---- gpt-5.4-mini / azure-openai-responses

Планируемое хранение:
Cloudflare Pages Functions ---- Cloudflare D1
```

Вызов `puter.ai.chat()` выполнялся непосредственно в браузере. Использовались `reasoning_effort: "minimal"`, `normalize: true` и structured output через `text.format` с JSON Schema. `max_tokens` явно не задавался. Puter Test mode обрабатывался тем же путём, что и обычный ответ.

### 5.3. Принятые решения

#### Почему выбрана архитектура Cloudflare

Первоначально для хранения материалов рассматривался PostgreSQL, а для размещения приложения — инфраструктура AWS. Рассматриваемая схема с отдельным application server и управляемой PostgreSQL потребовала бы нескольких инфраструктурных компонентов и могла создавать регулярные расходы даже при небольшом количестве пользователей.

При выборе production-инфраструктуры одним из основных ограничений была необходимость избежать обязательных регулярных расходов на раннем этапе проекта. Анализ распространённых надёжных hosting-платформ показал, что бесплатные тарифы чаще всего подходят только для статических сайтов. Бесплатный тариф Cloudflare Pages дополнительно позволяет выполнять Pages Functions без отдельного постоянно работающего сервера, а D1 предоставляет совместимое с этой serverless-моделью хранилище. Это позволяет разместить статический Next.js export и сохранить необходимые server-side операции в одной инфраструктуре.

Поэтому архитектура была изменена следующим образом:

- интерфейс собирается как статический сайт и размещается в Cloudflare Pages;
- динамические защищённые операции выполняются через Pages Functions;
- материалы хранятся в D1;
- PostgreSQL, Prisma, отдельный application server и AWS исключены из актуального production-стека;
- инфраструктура масштабируется от фактического использования и не создаёт обязательных расходов на постоянно работающие ресурсы на текущем этапе проекта.

Это решение снижает стоимость и операционную сложность, сохраняя необходимую серверную границу для проверки Puter-токена и безопасного доступа к пользовательским материалам.

#### Остальные решения

- Перевести Next.js в режим статического export и публиковать через Cloudflare Pages.
- Сохранить Docker Compose как локальное окружение, но не использовать Docker как production hosting.
- Использовать Cloudflare Pages Functions для защищённых операций библиотеки.
- Использовать Cloudflare D1 вместо первоначально рассматривавшихся PostgreSQL, Prisma и собственного Next.js backend.
- Проверять Puter-токен в Function и использовать подтверждённый `puter_user_uuid` как владельца записей.
- Не сохранять Puter-токен в базе или логах.
- Не давать браузеру прямой доступ к D1.
- Сохранять готовую структурированную адаптацию, чтобы повторное открытие не создавало новый AI-запрос.
- Применять production-миграции D1 отдельной командой Wrangler до появления безопасной автоматизации.

## 6. Состояние проекта на 10 октября 2026 года

### 6.1. Статус

Основной end-to-end сценарий реализован: пользователь авторизуется через Puter, создаёт адаптацию, сохраняет её в личную библиотеку, повторно открывает, редактирует и удаляет материал. Приложение опубликовано через Cloudflare Pages, данные хранятся в D1, CI и production smoke-проверки работают.

Сценарий ввода текста с изображения подготовлен на уровне UI и файловой валидации. Tesseract.js был проверен, но отклонён из-за недостаточного качества распознавания реальных фотографий. Новый OCR-движок пока не выбран.

### 6.2. Актуальная архитектура

```text
Браузер: статический Next.js / React
       |
       +---- Puter Auth ---- пользовательская сессия
       |
       +---- Puter AI ----- gpt-5.4-mini / azure-openai-responses
       |                    перевод и пояснения
       |
       +---- /api/materials ---- Cloudflare Pages Functions
                                  |
                                  +---- проверка Puter-токена
                                  |
                                  +---- Cloudflare D1

OCR: локальный browser-only feature-модуль; движок не выбран
```

- Production UI является статическим Next.js export. Постоянно работающего Next.js-сервера нет.
- Puter выполняет авторизацию и AI-генерацию.
- Pages Functions являются единственным шлюзом к D1.
- `GET /api/materials` возвращает только `id`, `title` и первые 320 Unicode-символов исходного текста.
- Полная запись загружается отдельным `GET /api/materials/:id` с `cache: "no-store"`.
- Preview и production используют разные D1-базы.
- Cloudflare Pages Git integration запускает production deployment после изменений в `main`.
- GitHub Actions выполняет CI и production smoke-проверки. Production-миграции D1 пока запускаются вручную через Wrangler.
- Изображение для OCR существует только в памяти вкладки и не отправляется в Pages Functions, Puter AI, D1 или localStorage.

### 6.3. Принятые решения

#### Библиотека и навигация

- Полная запись материала никогда не передаётся из списка как источник данных для reader: при открытии всегда выполняется detail-запрос.
- Обычная ссылка используется для перехода к reader, поскольку Cloudflare Function подставляет статический shell динамического маршрута.
- После новой несохранённой генерации внутренние переходы, Back и Logout защищаются диалогом. Закрытие и перезагрузка вкладки используют системное подтверждение браузера.
- Загруженный сохранённый материал без повторной генерации не считается несохранённым.

#### UI и mobile

- Высота страниц определяется CSS flex-layout, а не `ResizeObserver`, `window.innerHeight` или JS-вычислениями.
- Используется `100dvh` с fallback на `100vh`; длинный результат увеличивает страницу и сдвигает footer.
- Граница mobile/desktop layout — 720 px.
- Конфликты layout не решаются новыми `!important`; компоновка компонентов находится в CSS Modules.
- Общий footer размещён в root layout.

#### OCR

- OCR полностью изолирован в `app/new-text/_features/image-ocr`; диалог загружается лениво.
- Wizard разделён на шаги: выбор изображения → выбор языка → распознавание/результат.
- Диалог полноэкранный на mobile и закрывается только явными элементами управления, а не Escape или backdrop.
- Принимается одно изображение JPEG/JPG/PNG размером до 10 MB.
- Проверяются расширение, MIME-тип и сигнатура содержимого. Ошибка не удаляет ранее выбранное корректное изображение.
- `Take a photo` показывается только на мобильном устройстве, определённом не одной шириной viewport. Используется запрос основной камеры, но окончательный выбор камеры или галереи контролирует мобильный браузер.
- Для OCR используется отдельный dropdown. Подготовлены English и Russian; список можно расширить.
- Если textarea пуста, итоговое действие называется `Use this text`. Если текст уже есть, доступны `Replace current text` и `Add to current text`.
- После запуска распознавания должен сразу открываться третий шаг с круговым progress и крестиком отмены внутри; pause/resume не требуется.
- Tesseract.js технически работал полностью локально: npm-пакет, worker, WASM и модели English/Russian не использовали CDN.
- Качество Tesseract.js оказалось недостаточным для цели проекта: пользователь должен сфотографировать текст и получить результат, достаточно точный для последующих AI-пояснений.
- Tesseract.js удалён из runtime-кода, зависимостей, тестов, логов и локальных OCR-ресурсов. UI-каркас сохранён, запуск распознавания временно отключён.
