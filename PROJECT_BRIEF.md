# Веб-приложение для чтения по методу Франка

Дата: 17 сентября 2026 года.
Обновлено: 27 сентября 2026 года.
Статус: рабочий прототип генерации и отображения адаптации. Хранение материалов и backend-интеграция отложены.

## Архитектурный апдейт от 27 сентября 2026 года

Чтобы приложение можно было публиковать как статический сайт без постоянно работающего Next.js-сервера, для следующего этапа выбрана платформа Cloudflare:

- Next.js переводится в режим статического экспорта и публикуется через Cloudflare Pages;
- Docker и Docker Compose сохраняются как поддерживаемый способ локального запуска, разработки и передачи проекта другим пользователям;
- текущий Docker Compose запускает один web-контейнер: сначала применяет локальные D1-миграции, затем поднимает Cloudflare Pages runtime на порту 3000 и проксируемый Next.js dev server на внутреннем порту 3001;
- локальные данные D1 сохраняются в каталоге `.wrangler`; PostgreSQL-сервис больше не входит в актуальный Compose-файл, но первоначальное решение о PostgreSQL сохранено ниже как история архитектуры;
- браузерный вызов Puter AI сохраняется без изменений;
- защищённые операции библиотеки выполняются через Cloudflare Pages Functions или Workers;
- сохранённые материалы хранятся в Cloudflare D1 вместо PostgreSQL;
- браузер передаёт Puter-токен функции в заголовке `Authorization: Bearer <token>`;
- функция проверяет токен через Puter, получает подтверждённый стабильный `puter_user_uuid` и использует его как идентификатор владельца материалов;
- Puter-токен не сохраняется в D1, не включается в URL и не должен попадать в логи;
- браузер не получает прямого доступа к D1, а все чтения, сохранения и удаления материалов проходят через функцию после проверки пользователя.

Предыдущие решения о PostgreSQL, Prisma и собственном Next.js backend сохранены ниже как первоначальный вариант архитектуры. Для целевой публикации их заменяет описанная выше статическая архитектура Cloudflare. Docker-файлы при переходе сохраняются: они нужны для воспроизводимого локального запуска и возможности поделиться проектом с друзьями, но не являются целевой production-инфраструктурой. Старый неиспользуемый API-маршрут Anthropic удалён.

## 1. Цель

Пользователь вводит текст на испанском и получает материал для изучения: исходные фрагменты, перевод и полезные пояснения. Язык перевода и пояснений передаётся модели отдельным общим параметром для всего запроса. В текущем интерфейсе он задан константой; выбор языка пользователем ещё не реализован.

Сохранение готовых материалов в личную библиотеку остаётся целью проекта, но не входит в текущий этап работ.

## 2. Сценарий MVP

1. Пользователь открывает страницу обработки текста.
2. Вставляет испанский текст в текстовое поле и запускает адаптацию.
3. Если пользователь ещё не авторизован в Puter, приложение вызывает вход через Puter.
4. Браузер отправляет структурированный запрос через Puter AI и показывает состояние обработки.
5. Приложение проверяет структуру ответа и показывает исходный текст, переводы и пояснения по фрагментам.

На текущем этапе сохранение, повторное открытие и удаление материалов не реализуются. Позже сохранение будет выполняться только по явному действию пользователя, а повторное открытие не должно создавать новый AI-запрос.

## 3. Формат результата

Результат состоит из последовательных фрагментов. Каждый фрагмент включает:

- исходный испанский текст, взятый из пользовательского ввода;
- естественный перевод на выбранный целевой язык;
- строку с полезными пояснениями, разделёнными переносами строк.

Исходный текст не запрашивается у модели и никогда не берётся из её ответа. Приложение заранее делит пользовательский ввод на фрагменты, назначает им ID и после ответа сопоставляет переводы и пояснения с исходными фрагментами по этим ID.

Текущая форма ответа:

```json
{
  "fragment-1": {
    "translation": "...",
    "explanation": "term — explanation\nterm — explanation"
  }
}
```

Корневой объект должен содержать каждый запрошенный ID ровно один раз и не иметь посторонних ключей. У каждого фрагмента разрешены только строковые поля `translation` и `explanation`.

Пояснения должны содержать только полезную информацию сверх полного перевода: неочевидные значения и выражения, грамматику в контексте, местоименные связи и вероятные опечатки. Обычный словарный перевод очевидного слова сам по себе не является пояснением. Для каждой встретившейся формы глагола обязательно указываются инфинитив и грамматические характеристики: для личной формы — время, наклонение, лицо и число; для инфинитива, герундия и причастия — соответствующая неличная форма без выдуманного времени или лица. Весь пояснительный текст, включая связку между формой глагола и инфинитивом, пишется на целевом языке.

### Деление на фрагменты

- Словом считается любая непустая последовательность символов между пробелами или границами строки. Пунктуация внутри такой последовательности не создаёт новое слово.
- Целевой фрагмент содержит от 5 до 50 слов и по возможности заканчивается предложением: точкой, восклицательным или вопросительным знаком.
- Если добавление следующего предложения превысит 50 слов, граница ставится после предыдущего предложения.
- Если одно предложение длиннее 50 слов, оно принудительно делится блоками не более 50 слов.
- Короткий остаток по возможности присоединяется или перераспределяется без превышения лимита.
- `Intl.Segmenter` для этого не используется.

### Структурированный ответ и проверка

- Модель должна возвращать данные по заранее определённой JSON-схеме, а не готовую HTML-разметку.
- Для задачи адаптации используется прямой structured output по JSON-схеме. Tool calling не применяется как замена схеме и не подключается без отдельной функциональной необходимости.
- Во время текущего браузерного прототипа приложение проверяет JSON, точный набор ID, типы и обязательные поля ответа до отображения результата. Одних TypeScript-типов недостаточно.
- Оригинал сохраняется полностью, потому что приложение использует собственные исходные фрагменты, а модель возвращает только перевод и пояснения.
- Ответ, не прошедший проверку структуры или соответствия оригиналу, не считается успешным и не может быть сохранён в библиотеку.
- В режиме разработки неразобранный ответ Puter может показываться как обычный экранированный текст для диагностики. Он не считается корректной адаптацией.
- Формат ответа провайдера приводится к единому внутреннему контракту приложения. Даже при строгом structured output runtime-проверка остаётся обязательной.

### Недоверенный исходный текст и защита от prompt injection

- Любой введённый пользователем текст считается недоверенными данными. Команды, вопросы и другие инструкции внутри него должны переводиться и объясняться как часть исходного материала, а не выполняться моделью.
- Инструкция приложения и исходный текст передаются модели раздельными сообщениями. Правила обработки находятся в системном сообщении, а исходный текст — в отдельном пользовательском сообщении, сериализованном как поле данных.
- Одним промптом невозможно гарантировать, что модель всегда проигнорирует вложенную инструкцию. Безопасность обеспечивается архитектурно: запрос адаптации не получает tools, web search, выполнение кода, доступ к PostgreSQL, файловой системе, секретам или произвольным внешним запросам.
- Приложение самостоятельно разбивает исходный текст на фрагменты и назначает им идентификаторы до обращения к модели. Модель возвращает только перевод и объяснение для известных идентификаторов; оригинал для отображения и хранения всегда берётся из введённого пользователем текста, а не из ответа модели.
- После ответа проверяются JSON, точный набор идентификаторов и строковые поля. Неизвестные, пропущенные или дублированные фрагменты не принимаются.
- Ответ модели также считается недоверенными данными. Он выводится только как экранированный текст и не передаётся в `dangerouslySetInnerHTML`, `eval`, SQL, команды операционной системы, URL или имена файлов без отдельной проверки.
- Таким образом, невозможно дать абсолютную гарантию семантически правильного поведения модели, но даже при успешной prompt injection модель не должна иметь технической возможности выполнить действие с побочным эффектом.

### Отображение материала

- Интерфейс приложения и все элементы управления — на английском. Исходный материал остаётся испанским; перевод и пояснения должны быть целиком на языке из общего поля `language`.
- Пример в системной инструкции добавляется только при точном совпадении языка примера с текущим целевым языком. Это предотвращает перенос русских или английских служебных формулировок в ответ на другом языке.
- Сначала показывается исходный текст целиком, затем пронумерованные фрагменты. Каждый фрагмент имеет собственную рамку и содержит исходный отрывок, перевод и подробное объяснение.
- При первом открытии результата развёрнут первый фрагмент, остальные свёрнуты. У свёрнутого фрагмента видны номер и начало исходного текста; нажатие на текст или стрелку раскрывает его. Есть команды раскрыть и свернуть все фрагменты.
- В раскрытом фрагменте перевод изначально скрыт, объяснение открыто. Перевод и объяснение можно показывать и скрывать независимо. Для перевода используются тот же цвет и шрифт, что и для исходного отрывка.
- Прокрутка допускается внутри длинного объяснения. Его высота ограничивается доступной высотой экрана с учётом остальной части фрагмента и рассчитана минимум на три строки. Исходный отрывок и перевод показываются целиком.
- Для интерфейса приоритетен настольный экран, но компоновка должна оставаться пригодной для узких экранов.

## 5. Архитектура и доступ к данным

```text
Браузер (React)
       |
       +---- Puter Auth
       |
       +---- Puter AI ---- azure-openai-responses / gpt-5.4-mini
```

Сейчас вызов `puter.ai.chat()` выполняется непосредственно в браузере. Системная инструкция и пользовательские фрагменты передаются раздельными сообщениями. Запрос не получает tools, web search или доступ к приложению и его данным.

Для AI-запроса используются `gpt-5.4-mini`, провайдер `azure-openai-responses`, `reasoning_effort: "minimal"`, `normalize: true` и прямой structured output через `text.format` с JSON Schema. `normalize` нормализует внешнюю форму ответа Puter, но не заменяет JSON Schema. `max_tokens` сейчас явно не задаётся. Переключатель Puter Test mode включён по умолчанию; тестовый режим должен обрабатываться тем же путём, что и обычный ответ, без подстановки локальной заглушки.

Будущий backend нужен для хранения материалов, проверки Puter-токена и сопоставления пользователя со стабильным `puter_user_uuid`. Puter-токен нельзя сохранять в PostgreSQL или логировать. Параметры PostgreSQL будут передаваться через переменные окружения; секреты не должны попадать в репозиторий или Docker-образ.

## 6. Хранимые данные

Хранение переводов на текущем этапе отложено. Для будущего сохранённого материала необходимы:

- идентификатор материала и идентификатор владельца;
- название;
- исходный текст;
- исходный язык и язык перевода;
- готовые структурированные блоки адаптации;
- дата создания.

Исходный язык и язык перевода хранятся раздельно. В текущем запросе целевой язык уже является отдельным общим параметром, но элемента интерфейса для его выбора пока нет.

Способ хранения учётных записей зависит от выбранного решения авторизации. Хранение несохранённых результатов и технических записей обработки пока не определено.

## 7. Docker и локальная разработка

Предусмотрены два контейнера:

- приложение Next.js;
- PostgreSQL с отдельным Docker volume для сохранения данных между перезапусками.

В поставку проекта должны входить `Dockerfile`, `compose.yaml`, `.env.example` и инструкция запуска. После заполнения `.env` целевой запуск:

```bash
docker compose up --build
```

Приложение должно быть доступно по адресу `http://localhost:3000`. Установка Node.js и PostgreSQL на компьютер не требуется; нужны Docker с Compose, интернет и ключ выбранного ИИ API.

Для разработки предусматривается обновление приложения при изменении кода без пересборки образа после каждой правки. Применение миграций Prisma включается в процедуру запуска; конкретный механизм определяется при реализации.

Названия коммитов и их описания в Git пишутся на английском языке.

Контейнер приложения обращается к внешнему ИИ API через исходящие HTTPS-запросы. Дополнительные входящие порты для этих запросов не нужны. Доступ зависит от сетевых настроек компьютера, VPN и firewall.

## 8. Ограничения и обработка ошибок

Для текущего прототипа исходный текст ограничен одновременно 300 словами и 3000 символами. Текст, превышающий хотя бы один из лимитов, не отправляется на обработку. Пока AI-запрос выполняется в браузере, эти ограничения проверяет клиент; будущий backend обязан повторять проверку.

Ограничения количества запросов для контроля стоимости и времени обработки пока не согласованы.

Интерфейс должен показывать состояние обработки и понятную ошибку при недоступности API, превышении лимита или некорректном ответе. Ошибка обработки не должна отображаться как успешная адаптация.

### Ограничения Puter AI, отображаемые в интерфейсе

Интерфейс должен различать как минимум следующие ситуации:

- пользователь не вошёл в Puter или его токен больше недействителен — предложить войти повторно;
- месячный allowance или приобретённые кредиты исчерпаны (`insufficient_funds`) — объяснить, что расходы относятся к аккаунту пользователя, и предложить проверить баланс Puter;
- выбранная возможность требует платного тарифа (`subscription_required`) — сообщить об ограничении тарифа без автоматических повторов запроса;
- превышен лимит частоты или конкурентных запросов (`too_many_requests`) — предложить повторить попытку позже;
- Puter или внешний провайдер модели временно недоступен — показать повторяемую техническую ошибку без потери введённого текста;
- модель вернула ответ, не соответствующий внутренней схеме или оригиналу — сообщить, что материал не удалось корректно обработать.

Во время обработки повторная отправка формы блокируется. Точные размеры бесплатного allowance, стоимость моделей и лимиты не зашиваются в интерфейс, поскольку они могут меняться и зависят от аккаунта пользователя и выбранной модели.

Необходимость фоновой очереди определяется после замеров времени обработки. Отдельный обработчик фоновых задач пока не включён в принятый стек.

## 9. Риски использования Puter

- Puter-токен является секретом, позволяющим выполнять разрешённые операции от имени пользователя. Он передаётся только по HTTPS в заголовке `Authorization`, не записывается в PostgreSQL, не включается в URL и не попадает в логи.
- Будущий backend не должен доверять данным пользователя из браузера и обязан подтверждать каждый новый или ещё не закэшированный токен через Puter. В PostgreSQL владельцем материалов выступает стабильный `puter_user_uuid`, а не username или email.
- Компрометация клиентского JavaScript через XSS может привести к краже токена. Необходимы строгая Content Security Policy, отказ от небезопасной HTML-вставки и контроль сторонних зависимостей.
- Исходный текст и инструкции обработки передаются Puter и выбранному внешнему провайдеру модели. До публикации приложения необходимо проверить актуальные условия обработки и хранения данных и отразить их в пользовательской политике конфиденциальности.
- Доступность моделей, цены, allowance и ограничения Puter могут меняться. Идентификатор модели хранится в конфигурации приложения, а ошибки лимитов и недоступности обрабатываются без предположения о постоянных значениях.
- Поведение и формат ответов могут различаться между моделями и провайдерами. Приложение использует единый внутренний контракт, runtime-валидацию и тестовый набор эталонных текстов.
- Выход пользователя из интерфейса и завершение локальной сессии должны очищать состояние авторизации приложения. Backend не хранит Puter-токен для фонового или повторного использования без отдельного обоснования.

## 12. Критерии готовности MVP

- Проект запускается локально через Docker Compose по инструкции.
- Пользователь может войти через Puter, отправить испанский текст и получить адаптацию с переводом и пояснениями на выбранном целевом языке.
- Каждый фрагмент показывает неизменённый исходный отрывок и позволяет независимо раскрывать перевод и пояснение.
- Материал можно сохранить, открыть из библиотеки без повторной генерации и удалить.
- Материалы недоступны другим пользователям.
- Сохранённые материалы остаются доступны после перезапуска контейнеров при сохранённом volume БД.
- Puter-токен не сохраняется в PostgreSQL, не логируется и не включается в URL.
- Пользователь видит состояние обработки и сообщения об ошибках.

Ближайший шаг: проверить качество и расход токенов на примерах из `example.txt`, затем добавить пользовательский выбор целевого языка. Backend и сохранение материалов остаются отдельным следующим этапом.
